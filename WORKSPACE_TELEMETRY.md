# Workspace telemetry foundation (v0.1.14)

Scope: TEL-01 / TEL-02 / TEL-08, initial deployment slice A1. Canonical schema is PWA-Core v0.1.4 `src/telemetry.js`; the identical vendored copy is `src/workspace-telemetry-schema.js`. No new Google OAuth scope or storage service. Existing network-v1 files are preserved, and new normal Drive events go to exactly one writer after explicit enrollment. Old pending v1 batches can still flush. Disabling unified collection returns to the previous network-v1 behavior; it does not revoke Google Drive or delete existing files. NETWORK_TELEMETRY=off still controls the legacy request/maintenance instrumentation; explicit v2 enrollment is independent.

## Deployment and use
1. Publish Core, GoogleDrive and GitManager patches through GitManager in manifest order. The repository workflows update downstream Gitlinks. There is no need to move unrelated PWA-Core pins or deploy the translation Worker for this schema-only Core change.
2. Verify `pwa-profiles-api` is deployed from GoogleDrive v0.1.14 (the existing worker name, same DO class/migration, same secrets). Its Wrangler entrypoint now uses a WorkerEntrypoint class with unchanged fetch behavior plus RPC methods. If Cloudflare is not connected to this repository, deploy from the updated checkout with `npx --yes wrangler@4 deploy` (existing account and secrets); do not recreate the worker. GitHub settlement alone does not prove Cloudflare deployment. Verify `pwa-git-api` deployment from GitManager v0.1.5 and refresh AppLauncher.
3. In GitManager Settings, unlock administration, select Enable telemetry archive. Status initially shows a pending enrollment event. Normal profile requests and backups generate more entries. Open Google Drive → AppLauncher Profiles → telemetry → v2 after ~15 minutes (or when 64 queued records triggers an early flush). Check a JSON chunk with schema 2, min/max event times and eventsSha256. Do not share credentials or private profile content. The full telemetry extraction UI is a later phase.
4. Settings shows pending/dropped, last upload, archive size (unknown until reconciliation), archive request/retry/429 totals, and Drive account storage quota if available. All current data is Drive instrumentation, not all provider telemetry. To stop, select Disable unified archive; unsaved pending records are explicitly discarded; already uploaded chunks stay in Drive. Revoking Google authorization also invalidates the capability and stops collection. Signing out of one device does not revoke offline authorization.

## Contract and security
RPC methods exposed by the existing `PROFILES` binding: `telemetrySession(origin, profileCookieHeader, action)` for status/enable/disable, `telemetryAppend(capability, events)` for append only. These are not public HTTP routes. Only trusted Workers in this Cloudflare account may call them. GitManager validates authorized Google identity and same-origin administrator session for enrollment/disable, then forwards only the Google profile session cookie to RPC. The account is derived from the verified signed profile session, never an arbitrary email/account ID supplied by a browser. Enrollment issues a signed, typed, generation- and authorization-epoch-bound one-year append capability; repeated enrollment renews it. GitManager keeps it in a private coordinator storage key, not the UI, job payloads or logs. No producer uses it yet. No public arbitrary ingest endpoint. Revocation/disable invalidate old capabilities; expiry requires explicit reenrollment. Future producers must not forward the capability to browsers. Do not log request payloads or RPC arguments.

## Archive behavior and limits
- Immutable JSON chunks under `telemetry/v2` (flat initially; filename contains freeze UTC date, actual min/max event milliseconds and random batch ID). Marked Drive appProperties `pwaTelemetry=v2`. Each batch includes events hash and count, dropped count and event span. Stable ID and content reconciliation after ambiguous writes; archive receipt and row deletion in one DO transaction. Existing network-v1 files remain readable; adapter is available for future report reader, not a bulk migration.
- Bounded spool: 256 pending rows, 64 records per batch, 4 KiB/event limit; reserve preferential eviction for high-priority error/terminal observations. Recent 1024 committed event IDs deduplicated plus pending IDs. Retries start at 15 minutes, exponential up to 6 hours; overflow and 48-hour unsaved expiry count as drops, never confirmed upload. Frozen batch older than 48 hours is discarded as unconfirmed, even if a previous remote write may have succeeded; future report reader must dedup by ID. No claim of infinite replay protection or complete capture. No unbounded per-event list of dropped records.
- Nonempty batches flush after ~15 minutes or early when full; maintenance once daily while opted in, bounded 4 listing pages and 8 deletions per pass, then a short follow-up if needed. Delete only marked v2 JSON chunks within dedicated folder; retention uses oldest event time in a chunk (may remove newer mixed records with older records). 30 days and 250 MiB target; size reconciliation is best effort with capped pagination and failures visible. Size is unknown on incomplete list; archive may temporarily exceed cap. No backup/profile deletion. Existing legacy cleanup unchanged. Disable stops scheduled v2 pruning. Drive requests are counted separately for archive operations; `about.get` storageQuota is provider reported when accessible, not a billing limit. No telemetry recursion.
- Account coordinator reuses serialized existing Drive writer: no Drive IO on append, but bounded alarm work can temporarily delay profile requests. Separate archive DO, compressed/date-partitioned chunks, long-term usage rollups, client IndexedDB queue, provider polling and full range extraction are pending. Storage settings are initial conservative defaults; actual free-tier cost and deployed alarm behavior need live verification. No dedicated GitHub runners for telemetry.
