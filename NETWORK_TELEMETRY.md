# Account-wide network performance telemetry (schema 1)

Introduced in PWA-GoogleDrive v0.1.10. This is a best-effort diagnostic stream for the owner of the connected Google Drive account, not an analytics service. It is enabled for authenticated cloud operations by default. It never reads the local profile registry to label events.

## Where to find it

In Google Drive, open **AppLauncher Profiles / telemetry**. JSON files are named `network-v1-YYYY-MM-DD-<random-batch-uuid>.json`. This folder is outside `profiles` and `objects`. The backup retention/garbage collection logic does not read or delete it. All profiles and apps using the account share this folder; app and operation labels permit grouping without profile IDs. Standalone Ciyan and hosted Ciyan share the same account-side telemetry when connected to the same Google account. No third-party collector, analytics endpoint, new OAuth scope, or new Cloudflare binding is required.

After the first eligible cloud operation, an alarm is scheduled about ten minutes later. Subsequent successful flushes are separated by at least one hour. Cloudflare alarms may execute later than their requested time. A new file is only made when there is data; opening the app without cloud operations does not cause periodic empty writes. Upload errors are retried hourly up to three times while idle; future authenticated cloud requests can re-arm the journal. The original frozen batch is retried under the same name, and an existing file is checked for identical content before acknowledging an ambiguous write.

For later analysis, download the `telemetry` folder as a ZIP from Drive (or select the relevant JSON files), then provide that ZIP to your reviewer. There is no need to download the separate `objects` or `profiles` folders. A batch's filename date is the UTC time it was frozen, not necessarily the dates of every event within it. Files older than approximately 30 days are pruned on later successful flushes, with bounded deletion work per flush; idle/disconnected accounts do not run a separate retention-only alarm. Save any historical files you want to keep elsewhere before expiry. Deleting telemetry files has no effect on backup history.

## Data collected

Each file has `schema`, `createdAt`, `droppedEvents`, and `events`. `droppedEvents` counts older journal entries overwritten before the batch was frozen. There are three event types:

| Kind | Contents |
| --- | --- |
| `request` | UTC timestamp; app label; operation label; HTTP status; account queue wait (`queueMs`); Worker service time (`serviceMs`); JSON request/response UTF-16 character counts; Drive request and retry counts; index hits/misses; full object scans; summed and maximum Drive fetch-to-response-header time; Drive 4xx/5xx/429 and transport-error counts. Commit operations also include `commitHeadMs`, `commitObjectsMs`, `commitRevisionMs`, and `commitPublishMs` when reached. |
| `backup` | UTC start time; random event ID for duplicate detection; app label and optional numeric app version; outcome; elapsed/preparation/head/preflight/upload/commit timings; exact section payload bytes attempted (excluding headers/JSON envelope); sections changed/reused, objects sent/created, cache/hash/serialization counts, request counts and HTTP status when known. |
| `maintenance` | Timings and Drive metrics for historical revision pruning and object garbage collection. No profile ID or folder name. |

`driveHeaderMs` sums individual fetch-to-header times, including concurrent requests; it is not total wall-clock time and can exceed `serviceMs`. `serviceMs` includes the Worker route, Drive response-body reads and processing, but excludes telemetry journal persistence. `queueMs` measures delay from arrival in the account coordinator until execution starts. Client backup phase times include browser-to-Worker round trips, parsing, and retries as performed by the existing backup logic. Missing timing/metric fields mean unavailable or not reached, not zero. `requestChars` and `responseChars` are string lengths, **not network bytes**. Client `payloadBytes` is actual UTF-8 section content, not total wire traffic. There is no profiling of local UI actions, external Azure speech requests, ordinary offline asset fetches, OAuth credentials, or unauthenticated traffic.

App labels are allowlisted (`ciyan`, `worldgen`, `ascendant`, `chronicle`, `applauncher`), with `other` for shared or unidentified operations. Future apps using the shared backup API automatically get a label once included in that allowlist. Apps not using this cloud API do not generate sync telemetry. No learning content, chapter text, dictionary entries, profile names/IDs, object hashes, raw routes, Google IDs, emails, session IDs, tokens, IP addresses, device fingerprints, or free-text errors are written. A random backup event ID has no relation to a profile or operation ID. Deduplicate client backup records using that ID if an acknowledgement was lost.

## Performance and failure isolation

- Normal browser requests carry at most three previous completed backup summaries, piggybacked in a bounded header. No additional browser request is generated, including on Home or Refresh. Summaries are retained in a small tab-session buffer (16) across ordinary reloads; a new session must be confirmed before it can receive them. They can be lost if the browser session is discarded or no subsequent cloud request occurs. The server-side request records still cover operations reaching the Worker.
- The account coordinator records one small bounded journal append in Durable Object storage per eligible request. This adds local storage/CPU work, but **no additional Google Drive operation in the foreground backup path**. A bounded ring retains the latest 1,024 events plus at most one frozen batch of 1,024 events during a failed flush. Journal failures are handled best-effort and must not be used to report a backup as failed. Telemetry does not affect cloud revision content or the local sync cursor.
- One alarm-driven file write (plus discovery/existence checks and occasional bounded pruning) replaces a write for every backup. The alarm uses the existing serialized account queue to respect authorization and Drive consistency, so occasional backups can wait behind a telemetry flush; queue timing makes such delays observable. There is no guarantee of zero overhead or zero lost telemetry.
- The Worker still enforces the same Google authorization, revision integrity, idempotency, and compare-and-swap rules. The telemetry journal is not a source of truth for backup completion. Sign-out leaves the account authorization and its pending telemetry intact; account-wide revocation stops future uploads and discards pending telemetry best-effort. Files already written to Drive remain yours.

To disable collection, set the optional Worker environment variable `NETWORK_TELEMETRY=off` and deploy. No new variable is necessary for default operation. Previously exported files remain until you delete them or collection is re-enabled and retention runs. The next pending alarm clears the local telemetry journal when disabled.

## Acceptance checks

The regression suite exercises privacy filtering, session scoping, ring overflow, durable restart, retry after a lost Drive-write acknowledgement, bounded retries, retention isolation, and journal failure handling. Test a live cloud profile after deployment; make a few edits, allow normal backups, and after the alarm has run inspect the Drive folder. Verify that files contain only the numeric metrics and allowlisted labels documented here. An exact real-device performance comparison requires live telemetry; local tests use a simulated Drive and alarm backend.
